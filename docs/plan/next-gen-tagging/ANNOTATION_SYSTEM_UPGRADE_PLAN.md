## 0. 评审结论与采纳决定（2026-08-15）

### 0.1 价值肯定（予以采纳）

1. **双轨解耦架构**：轨道 A 回答"哪个客观组件出了多少正/负评"（WHAT，定量监控），轨道 B 回答"哪种主观体验被哪种设计缺陷伤害"（WHY，定性归因），与工作室"舆情看板 + 深度用研"的真实分工同构，分析野心是对现行单一标注管线的实质升级。
2. **PEDM E 维度理论扎实**：E1-E6（心流/核心乐趣、学习掌握、投入留存、情绪沉浸、信任价值、社交生态）与业界玩家体验/动机框架高度同构；P1-P7 是归一化的"设计缺陷本体库"；E×P 本质是结构化定性编码本（codebook），属体验研究标准方法。
3. **Severity × Intent 象限有真实分诊价值**：流失风险 / Bug 反馈 / 建设性建议 / 纯吐槽，贴合研发消费 VOC 的优先级逻辑。
4. **垃圾防护（E0/P0）**：对中文 Steam 评测生态（纯梗/字符画/反讽）必要且清醒。
5. **两条边界纪律正确**：L3.5 手动触发（而非常驻聚类基建）、L3.5"只现象不归因"禁令，均适配本项目规模。
6. **GDT 词表质量**：L1×10 比现行 L1×7 正交性更好，平台与安全、本地化、DLSS/FSR、EA 完成度、暗改等节点更细分。

### 0.3 总体决定

> **不做整体替换。** 保留方案4"观点短语提取 → 程序匹配"骨架与证据链；新设计以**词表（GDT）、新功能（L3.5）、诊断能力（PEDM）**三个层次分阶段嫁接；监控形态功能（BI 大盘 / Spike 告警）**暂缓**，待数据规模达标后重评。

## 2. 分阶段待办（核心）

> 排序逻辑：前置依赖 + 业务价值/工作量比。每阶段有独立验收标准，未达标不进入下一阶段。

### 阶段 0 · 前置：时序数据持久化 🔴

- **问题**：定时任务当前每日全新库、不累积（README 已载明）——任何监控形态功能的地基不存在。
- **交付物**：定时采集的落库持久化方案（增量入单库 + 去重），与 DEVELOPMENT_PLAN P6 自动化联动落地。
- **验收**：连续 ≥2 周数据累积，评论量时序逐日稳定增长；时区统一为 tz-aware UTC（同步解决阻塞表已知项）。

### 阶段 1 · GDT 词表嫁接：只换词表，不换管线 🥇

- 以 GDT v3.1.1（本文档第 4 节）为新词表，替换现行 gaming.yaml（L1×7 / L2×28 / L3×128）。
- **保留方案4 骨架**：LLM 只提取观点短语，程序负责匹配；按新树重建 l3_definitions.yaml（每 L3：定义 + 关键词 + 黑话，如 CS2 挂壁/绿玩/开黑/坟头草）。
- **保留证据链**：opinions 落 quote + 字符偏移（quote_start/quote_end），新 Schema 不得丢弃。
- **合并落地 67% 兜底治理**（与 DEVELOPMENT_PLAN"当前最关键的一步"同一事项）：
  1. ~~bge 语义匹配：phrase ↔ L3 定义 embedding 相似度~~ **已证伪（2026-08-16 校准：`scripts/dev/calibrate_semantic_match.py`，bge-small-zh 对游戏黑话/专名 top-1 命中仅 19%、正确 L3 平均排名第 25，不足以做 L3 兜底）**；
  2. 收紧 ≤20 字无关键词兜底（**需谨慎：直接删除会导致正确样本保持率跌至 52.9%，已回退；需配合信号词/语义再收**）；
  3. 黄金集回归门禁 ✅ **已实现（2026-08-16：`tests/test_golden_match.py` + 410 条黄金集 `tests/fixtures/golden_match_set.json`）**。
- **搁置项**：v1.0 稿 5.1"GDT 封闭词表分类器 Prompt"（方案 A 已证伪，见 0.2-1）。
- **验收**：整体评价/其他兜底占比 topic 口径 ≤30%（当前 67%）；黄金集回归通过；现有 pytest 全绿；全量重打成本在年度预算内。

### 阶段 2 · L3.5 动态微话题：第一个新功能 🥈

- **保留 v1.0 两条纪律**：手动触发（分析师框选时间段 + L3 节点）；短语仅限微观对象/现象，严禁情感与归因词。
- **实现变更**：先用本地 bge embedding 聚类（零 API 成本），LLM 只做簇命名与整理；接口形态保留 POST /api/v1/insights/l35-cluster。
- **必须返回 sample_comment_ids** 供人工核验；窗口样本 <30 条时返回 low_sample_warning，禁止输出确定性结论。
- **验收**：1 款游戏 × 1 个 L3 节点下钻产出可人工核验的簇；簇名 0 情感/归因词（可脚本自动检查）；单次下钻成本 ≈ 0。

### 阶段 3 · PEDM 负向观点试点：先验证后放量 🥉

- **范围收窄**：仅对负向观点跑第二遍诊断（非全量文本）；复用 comment_opinions 的 phrase / full_path / sentiment 作为辅助上下文输入。
- **Schema 修正**：采用第 5 节修订接口——新增"证据不足"档（evidence_level）、证据 span、confidence、taxonomy_version 版本化指针。
- **定位修正**：输出为**"候选假设清单"**，非可直接派发 Task；聚合 + 人工确认后才进入研发任务流。
- **黄金集先行**：人工标注 50-100 条（覆盖 E 维度 / P 模式 / 证据充分性三列），测 LLM 一致率；目标 E 维度一致率 ≥80%（或 Cohen's κ ≥0.6）才放量。
- **验收**：黄金集一致率报告 + 单款游戏试点报告（含 10% 抽样人工复核记录与错误类型归类）。

## 4. GDT 词表修订 v3.1 → v3.1.1

**修订点**：
1. 新增头部"正交原则 / 匹配职责 / 归因裁定"规则（继承现行 gaming.yaml 头部 3 条裁定 + 新增 3 条）；
2. 综合推荐度 vs 总体体验评价：保留双节点，按"是否含明确推荐意图"裁定（规则 5）；
3. 匹配机制(网络侧) vs 组队开黑/匹配社交：按"网络质量归因 vs 玩家行为归因"裁定（规则 4）；
4. 跨游戏稀疏容忍：抽卡/反作弊/公会等强联机节点允许在特定游戏 0 命中，不强制归类；
5. 树结构本身与 v3.1 一致，不增删节点（降低阶段 1 重建词典工作量）。

## 5. 数据接口修订（v2）

> 相对 v1.0 稿的变更：全部标签结果强制携带证据 span；新增 taxonomy_version / analyzer 版本对账；
> PEDM 新增"证据不足"档与 confidence；target_entity_ref 版本化指针防词表演进孤儿引用。

```typescript
// 1. 原始评论输入（同 v1.0，未改）
export interface RawComment {
  comment_id: string;
  game_id: string;
  timestamp: string; // ISO8601
  text: string;
  rating?: number;
  playtime_hours?: number;
  platform?: string;
}

// 2. 轨道 A：GDT 打标输出（v2：+版本号 +证据链 +置信度）
export interface GDTLabelResult {
  comment_id: string;
  taxonomy_version: string; // 如 "gdt-3.1.1"
  tags: Array<{
    l1: string;
    l2: string;
    l3: string;
    sentiment: 'Positive' | 'Neutral' | 'Negative';
    evidence: { quote: string; start: number; end: number }; // 必填：继承方案4 证据链
    confidence?: number; // 0-1：语义匹配相似度或候选打分
  }>;
}

// 3. L3.5 动态微话题聚类结果（v2：+低样本预警）
export interface L35TopicClusterResult {
  l3_anchor: string;
  taxonomy_version: string;
  time_window: { start: string; end: string };
  low_sample_warning?: string; // 窗口样本 <30 条时的预警文本
  clusters: Array<{
    topic_id: string;
    topic_name: string; // 微现象短语，无情感/归因词

    volume_ratio: string;

  }>;
}

// 4. 轨道 B：PEDM 诊断输出（v2：+证据不足档 +证据 +置信度 +版本化指针）
export interface PEDMDiagnosisResult {
  comment_id: string;
  pedm_version: string;
  scenarios: Array<{
    evidence_level: 'Sufficient' | 'Insufficient'; // 新增：取代强制选择
    experience_dimension: string; // E1-E6 / E0；Insufficient 时为 "E_insufficient"
    problem_pattern: string;      // P1-P7 / P0；Insufficient 时为 "P_insufficient"
    target_entity_ref: {
      l3_path: string;            // GDT L3 标准路径
      taxonomy_version: string;   // 版本化指针
    };
    impact: {
      severity: 'S_Critical' | 'S_High' | 'S_Medium' | 'S_Low';
      user_intent: 'I_Churn_Risk' | 'I_Bug_Report' | 'I_Constructive_Advice' | 'I_Emotional_Vent';
    };
    symptom_description: string;
    evidence: { quote: string; start: number; end: number }; // 必填
    confidence: number; // 0-1
    actionable_input_for_dev: string | null; // 定位"候选假设"；P0 或 Insufficient 时为 null
  }>;
}
```

### 6.3 PEDM 诊断 Prompt（修订版：+证据不足档 +证据必填 +假设定位）

```text
System Instruction:
你是一个资深游戏主策划与体验诊断专家。请对输入的玩家评论（附观点短语提取结果作为上下文）
进行逻辑归因诊断。输出定位为"待验证的候选假设"，不是可直接派发的研发任务。

[边界处理与垃圾防护 (Garbage-In Guard)]
1. 若评论为正评、纯梗、字符画或无设计缺陷的吐槽：
   - evidence_level = "Sufficient"
   - experience_dimension = "E0_Meta_General"，problem_pattern = "P0_None"
   - actionable_input_for_dev 必须强行设置为 null。
2. 若评论含负面情绪但证据不足以支撑 E×P 归因（表述模糊、缺少具体对象/场景）：
   - evidence_level = "Insufficient"
   - experience_dimension = "E_insufficient"，problem_pattern = "P_insufficient"
   - actionable_input_for_dev = null。严禁强行选择。
3. 若评论包含有效痛点：
   - evidence_level = "Sufficient"
   - 从 PEDM E1-E6 中选择最贴切的体验维度，P1-P7 中选择最贴切的设计缺陷模式。
   - target_entity_ref.l3_path 必须从 GDT v3.1.1 的 L3 节点中选择标准路径
     （如 "机制与内容 -> 核心机制与循环 -> 战斗系统"），并携带 taxonomy_version。
   - 生成 actionable_input_for_dev，格式：【后端/策划/引擎分析输入】+ 具体可落地的优化建议。
4. 每个 scenario 必须携带原文证据 evidence.quote 与字符偏移，并给出校准后的 confidence。

输出 JSON 格式，遵照 PEDMDiagnosisResult 接口。
```
